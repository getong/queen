Two questions separate these systems more than any feature list: how you keep order per entity when
there are millions of entities, and what one commit covers when a service handles an event. Queen's
answers are a [partition per entity](/concepts/partitions/), created by its first message, and one
[transaction](/concepts/transactions/) that writes
the ack, the state, the next events and the timers as one entry. Every system below answers
differently, and each is better than Queen at something, which each section says. Laravel teams
that run Horizon on Redis have their own comparison: [Queen or Horizon](/guides/laravel/queen-vs-horizon/).

## Kafka

A Kafka topic has a number of partitions chosen when you create it; it can grow but never shrink.
The producer hashes each record's key onto a partition, so an entity shares its partition with
every other entity that hashes there, and a slow one delays the rest of its partition (head-of-line
blocking). Growing the
count can send a key's new records to a different partition, and then that key's order across the
change is lost. Since 4.2, share groups give Kafka queue-style consumption, with per-record acks
and a delivery limit, and they get there by giving up ordering.

A Kafka transaction makes writes to several partitions and the consumer's offsets atomic: read,
process, write. Kafka Streams, with `exactly_once_v2`, keeps its state inside that boundary by
writing it to changelog topics. State in your database stays outside it (KIP-939, which would let
Kafka join an external two-phase commit, is accepted but not released), and Kafka has no delayed
delivery.

Kafka is better at latency and throughput up to about ten thousand partitions, and at the cost of
getting them. In our runs (below) its median was three to six times lower than Queen's and its p99
lower too up to 10,000 partitions, it used less CPU up to 1,000, and one topic of 1,000 partitions
carried about 8,000,000 messages a second where one Queen queue carried 3,500,000; on 16-vCPU
nodes it kept up with 4,000,000 messages a second on 100 partitions, where Queen carried 2,000,000
and not 2,500,000. Kafka acknowledges a write once its replicas hold it in
memory, without waiting for an fsync, which is part of that difference. Then there is the ecosystem (Connect and its connectors, Streams, schema
registries) and log compaction. Queen's [Kafka facade](/guides/kafka/) lets existing producers and
consumers connect, and accepts the topic settings Streams and Connect create, but a compacted topic
keeps every record, because Queen does not compact.

## Pulsar

Pulsar's Key_Shared subscription keeps per-key order without a partition per key, its transactions
cover publishes and acks across topics, and it can delay delivery on shared subscriptions. Its
storage acknowledges after an fsync on two of three bookies, the same durability Queen gives, which
makes it the fairest comparison in our runs. A cluster runs brokers, BookKeeper bookies and a
metadata store (ZooKeeper, in our runs).

Pulsar is better at latency and CPU at 200 and at 10,000 partitions, where it beat Queen in our
runs, and at transaction throughput. With 10 messages per transaction, Pulsar sustained 14,400
transactions a second over 900 partitions (17,600 over 1,800, while falling behind); Queen's best
was 8,900, in one raft group. Pulsar's
transactions cover messages and acks, so your application's state still lives in another system,
and at 50,000 partitions Pulsar could not keep up with the load Queen carried.

## RabbitMQ

Producers publish to exchanges, and bindings route each message into queues. A queue delivers in
order, but competing consumers on one queue do not process in order. Per-entity order needs a
queue per entity (a queue per user, say), a consistent-hash exchange over a fixed set of queues each with a single active
consumer, or a super stream with single active consumers.

Channel transactions group a channel's publishes and acks, but RabbitMQ does not make them atomic
(a failure during the commit can leave some of them done), and AMQP 1.0, its core protocol since
4.0, has no transactions. State in your database is outside either.

RabbitMQ is better at routing. Exchanges, bindings, topic patterns and header matching have no
Queen equivalent; in Queen the producer names the queue and the partition. RabbitMQ also speaks
more protocols (AMQP 0-9-1 and 1.0, MQTT, STOMP, its stream protocol), where Queen speaks HTTP and
the Kafka wire protocol.

## Amazon SQS

FIFO queues keep order within a message group ID, and while a group has messages in flight, SQS
delivers no others from it. It is the closest idea to a Queen partition: a group needs no
declaration and there is no count to choose. Deduplication uses a deduplication ID inside a fixed
five-minute interval.

There is no transaction: deleting the input, sending the output and writing state are separate
calls, and even a batch send can partly succeed. A queue serves one set of consumers, so fan-out
goes through SNS or a queue per subscriber, and a deleted message cannot be read again. On FIFO
queues, a delay is a queue setting of at most 15 minutes, never one message's own time.

SQS is better when you want nothing to operate: there is no server to run, patch or back up, you
pay per request, and it scales without a partition count to think about.

## Temporal and Restate

Both are durable execution engines. You write the workflow as code; they record each step in a
history (Temporal) or a journal (Restate), and on recovery they replay your code against that
record. Per-entity order comes from addressing one workflow, or one Restate virtual object, by the
entity's key; Restate runs one exclusive handler at a time per key. Temporal needs deterministic
workflow code and a database behind it (Cassandra, MySQL or PostgreSQL), and caps one history at
51,200 events, so a long-lived workflow per entity has to continue-as-new. Restate journals an
object's state, its outgoing calls and its timers together with each step, which is the idea on
this page closest to Queen's. It is one Rust binary as well, clustered since 1.2, under the BSL
1.1 license.

Queen keeps the state machine as data instead of code: the partition is its input, KV is its
state, and one transaction is one transition. Any language that speaks HTTP can be the worker, and
nothing replays your code. It is also a broker, with consumer groups, fan-out to other groups and
replay of history. See [one state machine per entity](/guides/state-machines/).

Temporal and Restate are better for authoring long workflows as code, where loops, branches, waits
of days and compensations read as one function.

## PostgreSQL and a transactional outbox

This is the stack most teams build. A service writes its state and an outbox row in one database
transaction; a relay (a poller, or change data capture such as Debezium) publishes the outbox rows
to a broker; consumers keep an idempotency table so a redelivery is harmless; and a jobs table or a
scheduler handles time. Per-entity order holds if the relay publishes in commit order, keyed by the
entity. Queen 1.x itself kept all of its state in PostgreSQL; 2.0 keeps it in its own log.

The database transaction covers the state and the outbox row. The publish, the consumer's ack and
the consumer's own state write are separate commits, and the idempotency table and the
reconciliation code exist to stitch them together. [Exactly-once processing](/guides/exactly-once/)
shows the same consumer in Queen, where the marker and the ack commit as one entry.

PostgreSQL is better when your state is relational: SQL, joins, constraints and ad hoc queries,
with the backups and tooling you already run. Queen's [KV](/concepts/kv/) reads by key or
by prefix.

## Also worth a look

NATS JetStream deduplicates within a window (two minutes by default), and since 2.12 can publish
an atomic batch to one stream and schedule messages, but no transaction joins an ack with
publishes. Azure Service Bus sessions give FIFO per session ID on a session-enabled queue, with
nothing to declare per session, its transactions group sends and completions, and scheduled
messages are ordinary sends with a time attached. Of the managed services, it comes closest to the
shape described here.

## Measured side by side

We ran Queen 2.3.0 and Kafka 4.3.1 on the same three GCP nodes (`c4-standard-24-lssd`: 24 vCPU,
88 GB and local NVMe disks each, one VPC), with the same loaders: 256-byte JSON messages in batches
of 100, one topic or queue, 3,000,000 messages a second offered, CPU summed over the three nodes.
A latency is the median of the three 10-second windows in seconds 30 to 60 of the load, the worst
window's p99 in brackets (2026-10-14; the released image, with the binary wire forms its clients
turn on; Kafka on XFS with thread pools for 24 vCPU; the runs are listed on
[Queen vs Kafka on NVMe](/benchmarks/queen-vs-kafka/#the-runs)). Queen acknowledges after two of
three fsyncs; Kafka acknowledges once its in-sync replicas hold the write in memory.

| Partitions | Kafka: e2e p50 / p99, cores | Queen: e2e p50 / p99, cores |
|---|---|---|
| 10 | 6.4 / 11 ms (45), 14.9 | 37 / 76 ms (78), 18.6 |
| 100 | 6.0 / 7.5 ms (8), 18.5 | 21 / 54 ms (65), 23.0 |
| 1,000 | 6.0 / 8.1 ms (8), 21.0 | 21 / 47 ms (56), 22.4 |
| 10,000 | 8.4 / 21 ms (78), 52.8 | 24 / 61 ms (66), 23.3 |
| 25,000 | 58 / 105 ms (146), 57.0 | not run |
| 50,000 | not carried (601,000 of 3,000,000 msg/s pushed, p99 32 s) | not run |
| 100,000 | not carried (174,000 of 3,000,000 msg/s pushed, p99 38 s) | 23 / 53 ms (71), 23.4 |
| 1,000,000 | not run | 23 / 42 ms (47), 23.0 |
| 10,000,000 | not run | 23 / 46 ms (54), 23.4 |

Up to 10,000 partitions Kafka is the faster of the two: a median three to six times lower and a
p99 of 7.5 to 21 ms against Queen's 47 to 76. Queen's cost stays flat as partitions grow, because
a partition is a few rows of state; Kafka pays per partition, with about twice Queen's CPU at
10,000, 57 cores at 25,000, and 50,000 not carried. With 1 KB messages at 1,000,000 a second the
medians come close (Kafka 7.4 to 8.8 ms, Queen 9.4 to 11) and Kafka's p99 is still the lower one up
to 10,000 partitions (9.4 to 19 ms, Queen 26 to 47). On one topic of 1,000 partitions Kafka
carried about 8,000,000 messages a second at a p99 near 12 ms; one Queen queue of 1,000 partitions
carried 3,500,000 and not 4,000,000. With an fsync on every append, the durability Queen
gives, Kafka read 7.5 / 12 ms at 100 partitions and 8.1 / 11 ms with 1 KB messages at 1,000, but
95 / 281 ms at 10,000 partitions, where Queen read 24 / 61
([fsync runs](/benchmarks/queen-vs-kafka/#kafka-with-an-fsync-on-every-append)). On 16-vCPU nodes two days earlier, Kafka
kept up with 4,000,000 messages a second on 100 partitions, where Queen carried 2,000,000 and not
2,500,000 ([throughput](/benchmarks/throughput/)).

Pulsar was last run in September, on 16-vCPU machines and beside Queen
2.0.0-beta.2: at 1,000,000 messages a second it read a p99 of 21 ms on 200 partitions and 32 ms on
10,000, on 7 to 10 cores, and fell behind from 50,000 partitions. In those runs, with 10 messages
per transaction on 200 partitions at 9,000 messages a second, a Queen commit took 3 ms at p50 and
4 ms at p99, Kafka's 12 and 34 ms, Pulsar's 22 and 32 ms. These runs measure the brokers; your shape
decides which of them matters. The full set, Redpanda included, is on [benchmarks](/benchmarks/):
[Queen vs Kafka on NVMe](/benchmarks/queen-vs-kafka/), [partition count](/benchmarks/partitions/),
[throughput](/benchmarks/throughput/) and [transactions](/benchmarks/transactions/).

## Summary

| | Per-entity order from | Partition count to choose | One commit covers | You run |
|---|---|---|---|---|
| **Queen** | a partition per entity, created by its first message | none | the ack, KV state, pushes and timers, as one entry | one binary: one node, or a cluster of three or five |
| **Kafka** | the record key, hashed onto a partition | per topic, up front; it can only grow | records across partitions, and consumer offsets | Kafka brokers (KRaft) |
| **Pulsar** | the key, with Key_Shared | per topic, up front | publishes and acks across topics | brokers, bookies and a metadata store |
| **RabbitMQ** | a queue per entity, or a hash onto a fixed set of queues | the queues you declare | no atomic transaction | RabbitMQ nodes |
| **SQS FIFO** | the message group ID | none | no transactions | nothing: a managed service |
| **Temporal, Restate** | one workflow or virtual object per entity key | none | a step of your code (Restate: with the object's state) | their server (Temporal also needs a database), or their cloud |
| **PostgreSQL + outbox** | a sequence per entity, kept by the relay | none | the state and the outbox row; publish and ack commit separately | the database, a relay and a broker |

## Limits

These are Queen's, the ones that decide a comparison:

- There is no routing: no exchanges, bindings, topic patterns or header matching.
- Delivery is at-least-once. Effects inside Queen are exactly-once through
  [transactions](/concepts/transactions/) and [`transactionId` dedup](/concepts/dedup/); a call
  your worker makes to another system is outside any commit.
- A transaction is one call, inside one tenant. There is no interactive BEGIN and COMMIT.
- One leader orders every write of a raft group, which bounds one tenant's write rate. A hot
  partition is sequential by design.

The full list is on [limits](/reference/limits/), and the cases where another system fits better,
with what to use instead, are on [when not to use Queen](/start/when-not-to-use/).
